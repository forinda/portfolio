KickJS is a decorator-driven Node.js framework for TypeScript. Today it is 17 npm packages, runs on Express, Fastify or h3, and deploys to Node, Bun, Deno and Cloudflare Workers. It did not start that way, and it did not stay the biggest it ever was. This is the story of how it grew, why I deliberately made it smaller, and why it matters to me that a Kenyan engineer is building a layer other developers install.

## Where KickJS started

KickJS started as a personal scaffolding tool. I kept setting up the same kind of API project: the same folder structure, the same wiring for configuration, validation and routing. A generator that did that in seconds was the first version.

The repository's first commit is from 20 September 2025, and the first releases, 0.1.3 and 0.1.4, went out the same day. A month later, on 29 October, the commit history says "Add base infrastructure core for Kickjs". That is the point where a scaffolding tool started turning into a framework.

The frustration behind it was with the established frameworks. NestJS and platforms like it come with strong opinions about how things are done, a lot of boilerplate, and a lot happening behind the scenes. That makes it hard to understand what your own application is actually doing. Django is a similar case: it abstracts so much away from the developer that the path a request takes is easy to lose.

I wanted the opposite: transparency. A mathematical function takes an input and returns an output, and you can read the processing in between. I wanted a framework to work the same way: this is where the request comes in, this is where the response goes out, and the logic between them is plain code, not magic.

## What it grew into

The goal became a framework that sits between Express and NestJS: the structure of decorators, modules and dependency injection, without giving up control of what runs underneath.

A controller in KickJS doesn't know which HTTP engine it runs on. It speaks a request context, and the engine is chosen once, at bootstrap:

```ts title="src/index.ts"
import { bootstrap } from '@forinda/kickjs'
import { fastifyRuntime } from '@forinda/kickjs/fastify'

// Express is the default. Fastify is one option away, with the same modules and controllers.
export const app = await bootstrap({ modules, runtime: fastifyRuntime() })
```

Around that core came the pieces a production API needs: a CLI that scaffolds projects and modules, Vite-powered hot reload, type generation so route params and responses are typed end to end, a typed fetch client for the frontend, OpenAPI generation from Zod schemas, and an entry point that runs the same app as a `fetch` handler on Cloudflare Workers, Bun and Deno.

## Why it got smaller

At its widest, KickJS also shipped packages for authentication, cron jobs, email, OpenTelemetry, GraphQL, multi-tenancy, notifications, and adapters for Prisma and Drizzle. Twelve of those packages are now deprecated on npm.

They fall into three groups:

- **Merged into the core.** `@forinda/kickjs-core`, `@forinda/kickjs-http` and `@forinda/kickjs-config` became part of `@forinda/kickjs`. Each got a final release telling you what to import instead.
- **Replaced by recipes you own.** `auth`, `cron`, `mailer`, `otel`, `graphql`, `multi-tenant` and `notifications` stopped being packages. Each has a guide showing how to build the same thing in your project.
- **Replaced by a native database layer.** The Prisma and Drizzle adapters were early experiments. `@forinda/kickjs-db` took their place.

The reasoning is written into the KickJS docs. Domain layers like auth, multi-tenancy, audit and observability vary from project to project: different claim shapes, different session stores, different policy rules. When a framework ships an opinionated package for one of those, two things happen. Teams with edge cases either fork it or ask for features that grow the package for everyone. And the framework's release cycle gets tied to that domain, so upgrading the framework forces you to review your auth.

For me the moment was concrete. I bootstrapped an application that needed third-party authentication, and with the auth package everything was already wired up: plugins for every piece, setup done, all of it working. Then I realised how much magic that was. If someone wanted to extend it in a way I hadn't planned for, they would have to come to me, the framework maintainer, and ask for the feature.

That changed who I was building for. KickJS was no longer only for my own projects. Other developers would bring opinions that don't match mine, and the framework should give them room to express those opinions instead of making them sit on mine.

Databases made the same point. In the Python world there are two dominant ORMs, and your framework mostly picks for you: Flask projects reach for SQLAlchemy through Flask-SQLAlchemy, and Django projects use the Django ORM with its built-in models and migrations. I had started down a similar road, building scaffolds around Prisma and Drizzle. Then Prisma 7 came out and broke most of what I had set up. I sat down and asked myself whether I would keep maintaining other projects' breaking changes inside my framework. The answer was no. I would build the layers and the ways to use them, and let people choose the tools they want, without fighting the framework to do it.

## What replaced the packages

KickJS keeps shipping the primitives those packages were built from: `defineAdapter`, `definePlugin`, `defineContextDecorator` and the dependency injection container. An adapter that used to be a package becomes a few lines in your own code:

```ts title="src/auth/auth-adapter.ts"
import { defineAdapter } from '@forinda/kickjs'
import { AUTH_STRATEGIES, LoadAuthUser } from './load-auth-user'
import type { AuthStrategy } from './strategies'

export interface AuthAdapterOptions {
  strategies: readonly AuthStrategy[]
  defaultPolicy: 'protected' | 'open'
}

export const AuthAdapter = defineAdapter<AuthAdapterOptions>({
  name: 'AuthAdapter',
  register: (container, opts) => {
    container.registerInstance(AUTH_STRATEGIES, opts.strategies)
  },
  contributors: (opts) =>
    opts.defaultPolicy === 'protected'
      ? [LoadAuthUser.with({ on401: 'reject' }).registration]
      : [LoadAuthUser.with({ on401: 'allow' }).registration],
})
```

There is a real trade-off here. The auth guide says it plainly: each project now owns roughly 200 lines of auth code, and the framework owns only the primitives. In exchange, your auth changes when your product needs it to, not when KickJS releases.

## How the migration was handled

When I started, KickJS was just primitives, and I wasn't sure yet how they would hold up. I was also learning how to roll out a project of this size. I didn't know whether anyone else was using it, but I was building side projects on it myself, and those projects showed me the issues.

Releases were their own problem. For a long stretch I was shipping major version after major version. It was around version 3 that plugins and adapters arrived, and with them the philosophy KickJS still follows: an adaptable framework that conforms to your thinking and your opinions, not mine.

That philosophy shaped how I handled the breaking change to authentication. Instead of removing the package and leaving people to rebuild it, I wrote bring-your-own implementations. They show how KickJS did auth, expressed in your own code. Moving to the next major release then means refactoring only the pieces that need it, so the application keeps working the way it did before.

Every deprecated package also says where to go next. The npm notices for the merged packages say what to import from `@forinda/kickjs` instead and mark the final release. The notices for the recipe packages point to the guide that replaces them. The docs describe these migrations as one-way and additive: you move code into your project, and you don't lose behaviour.
